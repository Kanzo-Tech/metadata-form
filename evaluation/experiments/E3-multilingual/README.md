## Provenance — an earlier round, and why its results are not here

An earlier round of this experiment (2026-08-27) ran the same shapes and data
through four third-party SHACL products alongside rudof, to test the claim we
had drafted for §5: *"multilingual SHACL is specified but not implemented by
validators — `sh:message` with language tags gets flattened or dropped."*

**That round refuted the claim.** We did not find the failure we had assumed,
and the draft sentence was wrong as written.

Those runs have been removed from the harness and from `results/raw/`.
Publishing a survey of other people's validators — in either direction — at
those maintainers' own community venue is not what this paper is for.
**Consequently the paper makes no claim about other implementations at all**,
neither that they handle multilingual `sh:message` nor that they fail to. No
per-product behaviour is named or tabulated anywhere in E3.

The cost is stated plainly in the writeup: E3 no longer has evidence about how
widely multilingual `sh:message` is handled in practice. That claim got weaker,
and the paper must not smuggle it back in by implication.

## Findings

### 1. The multilingual case is unverified by the conformance suites

This is E3's strongest finding, and it needs no validator at all — it is a
corpus count over the W3C test suites themselves (`raw/16`).

Across the SHACL 1.0 suite (150 test graphs) and the SHACL 1.2 suite (426),
**zero** subjects carry two or more `sh:message` values. Exactly one subject in
each suite carries a language tag at all — `core/misc/message-001`, a lone `@en`
message. An implementation can pass the entire approved conformance suite while
handling one message in one language.

So the sentence of §2.1.5 that governs the multilingual case is unexercised by
any approved test. Behaviour there is **unconstrained by the conformance
process** — not observed to be wrong, simply never asked about. That is the
argument §5 should make.

### 2. Ours was in fact wrong there, until we fixed it

`@kanzo-tech/rudof-wasm@0.3.4` flattened every `sh:message` to a bare string at
the wasm ABI boundary, discarding the language tag: three sentences reaching the
React form with no way to tell Catalan from Spanish. `0.3.5` preserves it —
`message` changed from `string[]` to `{ value, language }[]`.

The loss was **not in the engine**. rudof's Rust core keys messages by
`Option<Lang>` and the upstream CLI has always printed the tags (`raw/09`,
`raw/10`). The loss was in our own serializer at the JavaScript boundary. Both
versions are on npm and install side by side; `run.sh` runs the same input
through both (`raw/12`, `raw/13`).

The fix has shipped in every release since. `raw/20` records the full published
version list: 0.3.4 to 0.3.10, with 0.3.10 the current `latest`. Only 0.3.4 lacks
the tags (`raw/00` is the 2026-09-02 list, 0.3.4 to 0.3.8).

This is an unverified-by-the-suite behaviour, found wrong in the only
implementation we can speak for. It is exactly the shape of the risk finding 1
describes, evidenced on ourselves.

### 3. Where rudof was non-conformant — fixed in the engine we ship

Both pinned builds, 0.3.4 and 0.3.5, add an engine message
(`"MinCount(1) not satisfied"`) to a result whose shape already declares three
`sh:message` values. §2.1.5 says such a result carries **exactly** the shape's
messages, and §3.6.2.7 permits a generated message only when the constraint has
none. The upstream CLI 0.3.14 still does this in its Turtle report (`raw/09`).

**The current engine, 0.3.10, does not** (`raw/17`, asserted by `run-current.sh`,
`raw/19`): a result whose shape declares `sh:message` carries exactly those
messages, tags intact (three for the constraint with `@en`/`@es`/`@ca`, one
untagged for the control), and nothing the engine generated. A result whose shape
declares none (`data/shapes-nomsg.ttl`, `raw/18`) carries engine-generated
messages in **en, es and ca** (from the RDF catalog of `sh:message` templates on
constraint components), all language-tagged.

### 4. Two further facts about the current upstream rudof CLI

The default `compact` renderer's `Details` column stays empty, so
`rudof validate -M shacl` shows no message at all unless `-r details` is passed
(`raw/08` vs `raw/10`); and `-r json` panics on an unimplemented branch rather
than returning an error (`raw/11`). Neither bears on language tags. Both are
recorded because they are ours — the CLI is the same engine family seen from the
other side of the binding.
