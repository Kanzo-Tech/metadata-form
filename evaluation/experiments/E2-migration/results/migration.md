### Agreement checks

Each check compares, case by case, the conformance verdict **and** the exact
set of base-shape results `(focus node, path, constraint component)` — so a
pair that agrees on `conforms` but disagrees on *why* fails. `make check`
exits non-zero if any of these breaks.

| Check | holds | what it establishes |
|---|:--:|---|
| `rudof(implication) == rudof(shacl12-if)` | yes | the migration is behaviour-preserving: same verdict, same base-shape results, all 11 cases |
| `rudof(shacl12-if) == expected` | yes | and the behaviour preserved is the *right* one — the 1.2 encoding matches the requirement fixed in advance |
| `rudof(implication) == expected` | yes | the 1.0 encoding it is compared against is itself correct, so the equivalence is not two engines agreeing on a mistake |
| `rudof(shacl12-if) base results == rudof(shipped) base results` | yes | the conditional overlay adds a conditional and disturbs nothing else in the profile |

### Divergences — each one a finding

These pairs must *not* agree. The first case where each parts company:

| Pair | identical? | first divergence | what it shows |
|---|:--:|---|---|
| `rudof(shipped) != rudof(implication)` | no | 04-personal-data-no-legal-basis (conformance) | the published profile does not enforce its own prose |
| `rudof(partition-subjectsof) != rudof(implication)` | no | 08-personal-data-on-non-dataset (conformance) | `sh:targetSubjectsOf` leaks outside the class — the cheap SHACL 1.0 idiom is *wrong* |
| `rudof(partition-sparql) != rudof(implication)` | no | 04-personal-data-no-legal-basis (conformance) | rudof does not implement `sh:SPARQLTarget`; it silently ignores the shape, so the SPARQL partition is untested here |

The last row is a limit of this experiment and of our own engine, stated
plainly: rudof does not implement `sh:SPARQLTarget`, so the

Tab. 1 for its *structural* cost — the size of the SPARQL string a correct
SHACL 1.0 partition needs — and that measurement does not need a validator.

## 5. Listing 1 — the fragment for the paper

**Before** — SHACL 1.0, the shape partition. Two entry points on one class, a
target chosen to coincide with the condition, and the condition written a
second time as a field the form must hide:

```turtle
hri:PersonalDataDatasetShape a sh:NodeShape ;      # a SECOND entry point on dcat:Dataset
  sh:targetSubjectsOf dpv:hasPersonalData ;        # the target IS the condition
  sh:property [ sh:path dpv:hasPersonalData ;      # …and the condition, again,
                sh:minCount 1 ;                    #    as a field the form must hide
                dash:hidden true ] ,
              [ sh:path dpv:hasLegalBasis ; sh:minCount 1 ; sh:nodeKind sh:IRI ;
                dash:viewer dash:URIViewer ; dash:editor dash:URIEditor ] ,
              [ sh:path dpv:hasPurpose    ; sh:minCount 1 ; sh:nodeKind sh:IRI ;
                dash:viewer dash:LabelViewer ; dash:editor dash:URIEditor ] .
```

It is also **wrong**: `sh:targetSubjectsOf` selects every subject of
`dpv:hasPersonalData`, dataset or not (case `08`). Making it correct in SHACL 1.0
means moving the condition into a SPARQL string
(`data/before/overlay-02-partition-sparql.ttl`), where no structural tool can
read it, or writing it backwards as `sh:or ( [ sh:not C ] T )`
(`data/before/overlay-03-implication.ttl`).

**After** — SHACL 1.2. One entry point, no stamp, no target, and the condition
read in the order it is thought:

```turtle
hri:DatasetShape                                   # the published shape, unchanged
  sh:if   hri:PersonalDataCondition ;
  sh:then hri:PersonalDataRequirements .

hri:PersonalDataCondition a sh:NodeShape ;
  sh:property [ sh:path dpv:hasPersonalData ; sh:minCount 1 ] .

hri:PersonalDataRequirements a sh:NodeShape ;
  sh:property [ sh:path dpv:hasLegalBasis ; sh:minCount 1 ; sh:nodeKind sh:IRI ;
                shui:editor shui:IRIEditor ;
                sh:message "A dataset that declares personal data must state its legal basis."@en ] ,
              [ sh:path dpv:hasPurpose    ; sh:minCount 1 ; sh:nodeKind sh:IRI ;
                shui:editor shui:IRIEditor ] .
```

(Both listings inline the property shapes to fit a column; the files are
`data/before/overlay-01-partition-subjectsof.ttl` and
`data/after/overlay-04-shacl12-if.ttl`.)

## 6. Where SHACL 1.2 does *not* replace the DASH-era pattern

Four cases from the same corpus, stated plainly because they bound the claim.

**(a) A disjunction is not a conditional.** The only logical constraints anywhere
in the Health-RI corpus are in the DCAT-AP shapes it vendors (Health-RI ReusedCommunityStandards/dcatap.shapes.ttl (DCAT-AP 2.0)):
2 `sh:or`, each held by a node shape with **no target**, existing only so
that other property shapes can point at it:

| targetless shape | referenced by |
|---|---:|
| `DateOrDateTimeDataType_Shape` | 10 property shapes |
| `DcatResource_Shape` | 1 property shape |

`sh:if` is no improvement here. `DateOrDateTimeDataType_Shape` says *a date or a
dateTime*; there is no condition and no branch, and rewriting it as
`sh:if`/`sh:else` would be strictly worse. **SHACL 1.2 replaces `sh:or` only where
`sh:or` was standing in for an implication** — which is exactly the
`sh:or ( [ sh:not C ] T )` row of Tab. 1 and nothing else.

**(b) A `sh:hasValue` stamp is sometimes a real constraint.** The corpus has
1, in the same DCAT-AP file:

- `http://spdx.org/rdf/terms#algorithm` **=** `http://spdx.org/rdf/terms#checksumAlgorithm_sha1` (`sh:minCount 1`, `sh:maxCount 1`)

A DASH form renders it as a field with exactly one legal value, which is the
ugliness — but the constraint itself is correct and must survive. What removes it
from the *form* is a UI annotation, not a conditional. The stamps a conditional
does remove are the ones that exist only to re-state a discriminator inside a
branch shape (Tab. 1, `dash:hidden` column): 1 per branch, 0 after.

**(c) A partition whose discriminator is not in the data.** Where the DASH-era
profile split into N node shapes on one `sh:targetClass` and let the *application*
choose which one to load, `sh:if` cannot express it: `sh:if` reads a condition off
the focus node, so the discriminator must be a value in the graph. That is a
better design — the record then carries the reason it was validated the way it
was — but it is a change in the data model, not a pure re-encoding, and a
migration report should say so.

**(d) A partition that needs SPARQL cannot be checked here.** rudof does not
implement `sh:SPARQLTarget`, so `partition-sparql` is measured structurally in
Tab. 1 and unvalidated in Tab. 2. See §7.

## 7. Threats to validity

**The equivalence is demonstrated in one engine only.** Every row of Tab. 2 is
rudof. That is a deliberate choice — the claim is that the migration preserves
behaviour *in the engine that drives the form*, and rudof is that engine, so a
result from any other implementation would not settle the question being asked.
But the consequence must be stated: **an encoding difference that both encodings
happen to hit the same way in rudof would not be detected here.** If rudof's
`sh:if` and its `sh:or ( [ sh:not C ] T )` share a bug — a mis-scoped focus
node, a mishandled empty branch — the two rows would agree and this experiment
would call that agreement equivalence. What Tab. 2 rules out is divergence
*between the encodings under rudof*, not divergence from the SHACL
specification. The `== expected` checks narrow that gap on these eleven cases —
the verdicts were fixed before any run — but eleven cases are eleven cases.

**The tooling cost of adopting SHACL 1.2 is unmeasured.** How many deployed
validators understand `sh:if` today is a real question for anyone weighing this
migration, and this experiment does not answer it. An earlier revision reported
one datum from a second engine; that datum is withdrawn, and nothing replaced
it. A profile that migrates to SHACL 1.2 conditionals should expect uneven
support across the tools it is validated by, and should establish that support
for its own toolchain rather than take it from here.

**The structural measurements need no validator.** §1, §2, §3 and §6 — the shape
and triple counts, the DASH inventory, the isomorphism of the non-UI subgraph,
the `sh:or` census — are graph measurements made with rdflib. They stand
independently of which engine validates, and nothing above weakens them.

**One profile, one requirement.** The subject is a single published profile and
a single conditional requirement drawn from it. The five encodings are ours, so
they are as fair as we made them; the overlay files are in the repository to be
read and disagreed with.
